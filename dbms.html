FUNDAMENTALS
Q1 Which of the following is a DDL command? ▾
a) SELECT
b) INSERT
c) ALTER
d) UPDATE
ANSWER: C
DDL (Data Definition Language) defines database structure. ALTER, CREATE, DROP, and TRUNCATE are DDL commands. SELECT, INSERT, and UPDATE belong to DML (Data Manipulation Language).
Q2 Which normal form removes partial dependency? ▾
a) 1NF
b) 2NF
c) 3NF
d) BCNF
ANSWER: B
A relation is in 2NF if it is in 1NF and every non-key attribute is fully functionally dependent on the entire primary key — i.e., no partial dependency exists. 1NF only requires atomic values; partial dependencies are addressed at the 2NF level.
Q3 In ACID properties, "D" stands for: ▾
a) Dependency
b) Durability
c) Data integrity
d) Distribution
ANSWER: B
Durability guarantees that once a transaction is committed, its changes persist permanently in the database — even in the event of a system crash, power failure, or hardware failure. This is typically achieved through write-ahead logging.
Q4 A relation is in BCNF if for every functional dependency X → Y, X is a: ▾
a) Primary key
b) Foreign key
c) Super key
d) Candidate key only
ANSWER: C
BCNF (Boyce-Codd Normal Form) requires that for every non-trivial FD X → Y, X must be a super key. This is stricter than 3NF — every BCNF relation is in 3NF, but not every 3NF relation is in BCNF.
Q5 Which SQL keyword is used to remove duplicate rows from a result? ▾
a) UNIQUE
b) DISTINCT
c) DIFFERENT
d) FILTER
ANSWER: B
The DISTINCT keyword is used with SELECT to eliminate duplicate rows from the result set. UNIQUE is a constraint (not a query keyword), and the other options are not valid SQL keywords.
INDEXING & JOIN
Q6 In a B+ Tree, data pointers are stored only in: ▾
a) Root node
b) Internal nodes
c) Leaf nodes
d) All nodes
ANSWER: C
In a B+ Tree, all actual data pointers are stored only at the leaf nodes. Internal nodes store only key values and node pointers (acting as routers). Leaf nodes are linked for efficient range queries.
Q7 Which of the following is NOT a type of join in SQL? ▾
a) INNER JOIN
b) LEFT JOIN
c) CROSS JOIN
d) DEEP JOIN
ANSWER: D
"DEEP JOIN" is not a standard SQL join type. The standard join types are INNER, LEFT, RIGHT, FULL, and CROSS JOIN. NATURAL JOIN and SELF JOIN are also valid variations.
CONCURRENCY & LOCKS
Q8 A schedule is conflict serializable if its precedence graph has: ▾
a) A cycle
b) No cycle
c) Self loops
d) No edges
ANSWER: B
A schedule is conflict serializable if and only if its precedence graph has no cycles. The presence of a cycle indicates the schedule is not conflict equivalent to any serial schedule.
Q9 A shared lock (S-lock) allows: ▾
a) Read and write
b) Read only
c) Write only
d) Neither read nor write
ANSWER: B
A shared (S) lock permits only read operations on the locked data item. Multiple transactions can simultaneously hold shared locks. An exclusive (X) lock permits both read and write and is held by only one transaction at a time.
Q10 Two-Phase Locking guarantees: ▾
a) Deadlock freedom
b) Conflict serializability
c) View serializability
d) Atomicity
ANSWER: B
Two-Phase Locking (2PL) guarantees conflict serializability. It does NOT guarantee deadlock freedom — in fact, 2PL can lead to deadlocks. Strict 2PL also provides cascadeless rollbacks.
Q11 Deadlock in DBMS occurs due to: ▾
a) Too many transactions
b) Circular wait for locks
c) Slow disk I/O
d) Large database size
ANSWER: B
Deadlock occurs when each transaction in a set is waiting for a lock held by another transaction in the same set, forming a circular wait. The four necessary conditions are: Mutual Exclusion, Hold and Wait, No Preemption, and Circular Wait.
SQL & KEYS
Q12 Which key can have NULL values? ▾
a) Primary key
b) Foreign key
c) Composite key
d) Super key
ANSWER: B
A foreign key can contain NULL values unless explicitly constrained with NOT NULL. Primary keys cannot contain NULLs (they enforce entity integrity).
Q13 The minimum super key is called a: ▾
a) Primary key
b) Candidate key
c) Foreign key
d) Composite key
ANSWER: B
A candidate key is a minimal super key — no proper subset of it is a super key. The primary key is one candidate key chosen by the designer.
Q14 Which clause is used to filter results of GROUP BY? ▾
a) WHERE
b) FILTER
c) HAVING
d) ORDER BY
ANSWER: C
The HAVING clause filters groups after GROUP BY aggregation. WHERE filters individual rows before grouping. FILTER is not a standard SQL clause at the group level.
Q15 Which aggregate function ignores NULL values? ▾
a) COUNT(*)
b) SUM(col)
c) Both a and b
d) Neither
ANSWER: B
SUM(col) ignores NULL values in its calculation. COUNT(*) counts all rows including those with NULLs. COUNT(col) also ignores NULLs in the specified column.
Q16 GRANT and REVOKE belong to which SQL category? ▾
a) DDL
b) DML
c) DCL
d) TCL
ANSWER: C
GRANT and REVOKE are DCL (Data Control Language) commands used to manage database permissions. DDL = CREATE, ALTER, DROP; DML = SELECT, INSERT, UPDATE; TCL = COMMIT, ROLLBACK.
Q17 Which command removes all rows but keeps table structure? ▾
a) DELETE
b) DROP
c) TRUNCATE
d) REMOVE
ANSWER: C
TRUNCATE removes all rows but preserves the table structure. It is a DDL command and is faster than DELETE (DML, rows removed one by one). DROP removes the entire table including structure.
NORMAL FORMS & ER
Q18 Which normal form removes transitive dependency? ▾
a) 1NF
b) 2NF
c) 3NF
d) 4NF
ANSWER: C
3NF removes transitive dependency — where a non-key attribute depends on another non-key attribute. Formally: a relation is in 3NF if it is in 2NF and no non-key attribute is transitively dependent on the primary key.
Q19 In an ER diagram, a weak entity is shown with a: ▾
a) Single rectangle
b) Double rectangle
c) Dashed ellipse
d) Diamond
ANSWER: B
In ER diagrams: a weak entity = double rectangle; strong entity = single rectangle; multivalued attribute = double ellipse; derived attribute = dashed ellipse; relationship = diamond.
Q20 In ER diagrams, a multivalued attribute is shown with a: ▾
a) Single ellipse
b) Double ellipse
c) Dashed ellipse
d) Rectangle
ANSWER: B
A multivalued attribute (e.g., PhoneNumbers for an Employee) is represented by a double ellipse. Single ellipse = simple attribute, dashed ellipse = derived attribute, rectangle = entity.

ACID & NORMALIZATION
S1 Explain all four ACID properties with a real-life example for each. ▾
ANSWER
ACID stands for Atomicity, Consistency, Isolation, Durability.

1. Atomicity — All-or-nothing execution. Example: Bank transfer of ₹500 from A to B: both debit from A and credit to B must happen. If the system crashes mid-way, the entire transaction rolls back.

2. Consistency — Database moves from one valid state to another, preserving all rules. Example: After transfer, total balance A+B remains ₹1500. No constraint is violated.

3. Isolation — Concurrent transactions appear serial. Example: If T1 transfers money and T2 calculates total balance simultaneously, T2 sees either the state before or after T1 — not a partial state.

4. Durability — Committed changes are permanent. Example: After transfer confirmation, a power failure won't undo it — changes are in persistent storage via write-ahead logging.
S2 Differentiate between 2NF and 3NF with an example showing a relation that is in 2NF but not in 3NF. ▾
ANSWER
2NF removes partial dependency (non-key attribute depends on part of a composite key).
3NF removes transitive dependency (non-key attribute depends on another non-key attribute).

Example: Employee(EmpID, DeptID, DeptName, EmpName)
FDs: EmpID → DeptID, EmpName   and   DeptID → DeptName

2NF check: Since the primary key is a single attribute (EmpID), there is no partial dependency. ✓ In 2NF.

3NF check: There IS a transitive dependency: EmpID → DeptID → DeptName. DeptName depends on DeptID (non-key), not directly on EmpID. ✗ NOT in 3NF.

Decompose to 3NF:
R1(EmpID, EmpName, DeptID) — FK: DeptID → Department
R2(DeptID, DeptName)
S3 Write SQL queries using the table Student(RollNo, Name, Branch, Marks, City):
(a) Find all students from "Kolkata" with marks above 75.
(b) Count students in each branch.
(c) Find the branch with average marks greater than 70. ▾
ANSWER
(a)
SELECT * FROM Student WHERE City = 'Kolkata' AND Marks > 75;
(b)
SELECT Branch, COUNT(*) AS StudentCount FROM Student GROUP BY Branch;
(c)
SELECT Branch FROM Student GROUP BY Branch HAVING AVG(Marks) > 70;
HAVING filters groups after GROUP BY. WHERE filters rows before grouping.
TRANSACTIONS & KEYS
S4 What is Two-Phase Locking? Explain its growing phase and shrinking phase. Why does strict 2PL prevent cascading rollbacks? ▾
ANSWER
Two-Phase Locking (2PL) is a concurrency protocol that ensures conflict serializability by dividing transaction execution into two phases.

Growing Phase: Transaction acquires locks but may NOT release any. It gradually obtains all needed locks.

Shrinking Phase: Transaction releases locks but may NOT acquire any new ones. Begins after the "lock point".

Strict 2PL holds all exclusive locks until commit/abort. No other transaction can read uncommitted data. If a transaction aborts, no one read its dirty data — no cascading rollback needed.
S5 Explain the different types of keys in DBMS: Super key, Candidate key, Primary key, Composite key, and Foreign key. Give one example of each. ▾
ANSWER
1. Super Key — Any attribute set that uniquely identifies a tuple.
Example: {RollNo}, {RollNo, Name} in Student.

2. Candidate Key — Minimal super key (no proper subset is a super key).
Example: {RollNo} and {Email} if both uniquely identify.

3. Primary Key — Selected candidate key, cannot be NULL.
Example: RollNo chosen as PK.

4. Composite Key — Candidate key with multiple attributes.
Example: {StudentID, CourseID} in Enrollment.

5. Foreign Key — References PK of another table, enforces referential integrity.
Example: DeptID in Employee referencing DeptID in Department.
INDEXING & SERIALIZABILITY
S6 What is a B+ Tree? How does it differ from a B-Tree? Why is it preferred for database indexing? ▾
ANSWER
B+ Tree: A balanced multi-level index where all data pointers are in leaf nodes; internal nodes act as routers.

Differences from B-Tree:
FeatureB-TreeB+ Tree
Data pointersInternal & leaf nodesOnly leaf nodes
Internal nodesKeys + dataKeys only (routers)
Leaf linksNot linkedLinked list
Range queriesLess efficientHighly efficient
FanoutLowerHigher → shorter tree

Why preferred: Higher fanout → fewer disk I/Os; linked leaves → efficient range scans; shorter tree → stable search performance.
S7 Explain conflict serializability. Given the schedule S: R1(A), R2(A), W1(A), R2(B), W2(B), W1(B), identify conflicting pairs, draw the precedence graph, and state whether S is conflict serializable. ▾
ANSWER
Conflict Serializability: A schedule is conflict serializable if it can be transformed into a serial schedule by swapping non-conflicting operations. Two operations conflict if they belong to different transactions, access the same data, and at least one is a write.

Schedule: R1(A), R2(A), W1(A), R2(B), W2(B), W1(B)

Conflicting pairs:
OpsDataConflictEdge
R2(A) & W1(A)AYes (rw)T2 → T1
W2(B) & W1(B)BYes (ww)T2 → T1

Precedence Graph: T2 → T1 (two edges, no cycle)

Conclusion: No cycles → conflict serializable. Equivalent serial schedule: T2, T1.

SQL COMMANDS
S9 Explain DDL, DML, and DCL with examples of each. ▾
ANSWER
DDL (Data Definition Language) — Defines database structure/schema.
CREATE DATABASE db_name;
CREATE TABLE Student (RollNo INT PRIMARY KEY, Name VARCHAR(50));
ALTER TABLE Student ADD COLUMN City VARCHAR(30);
DROP TABLE Student;
TRUNCATE TABLE Student;

DML (Data Manipulation Language) — Manipulates data stored in tables.
SELECT * FROM Student WHERE City = 'Delhi';
INSERT INTO Student VALUES (101, 'Alice', 'Delhi');
UPDATE Student SET City = 'Mumbai' WHERE RollNo = 101;
DELETE FROM Student WHERE RollNo = 101;

DCL (Data Control Language) — Controls access permissions.
GRANT SELECT, INSERT ON Student TO 'user1'@'localhost';
REVOKE INSERT ON Student FROM 'user1'@'localhost';
CategoryCommandsEffect
DDLCREATE, ALTER, DROP, TRUNCATE, RENAMEAuto-commit (permanent changes)
DMLSELECT, INSERT, UPDATE, DELETECan be rolled back (if not auto-commit)
DCLGRANT, REVOKEImmediate effect on permissions
TCL (COMMIT, ROLLBACK, SAVEPOINT) is sometimes considered a separate category for transaction control.
SET OPERATIONS
S10 Explain UNION, INTERSECT, and MINUS (EXCEPT) set operations in SQL with examples. ▾
ANSWER
Set operations combine results from two or more SELECT queries. All queries must have the same number and compatible data types of columns.

1. UNION — Combines results of two queries, removing duplicates.
SELECT City FROM Customers
UNION
SELECT City FROM Suppliers;
UNION ALL keeps duplicates; UNION removes them.

2. INTERSECT — Returns rows common to both queries.
SELECT City FROM Customers
INTERSECT
SELECT City FROM Suppliers;


3. MINUS / EXCEPT — Returns rows from the first query that are NOT in the second.
SELECT City FROM Customers
EXCEPT
SELECT City FROM Suppliers;
MINUS in Oracle; EXCEPT in PostgreSQL/SQL Server.
OperationResult
A UNION BAll rows from A and B (no duplicates)
A INTERSECT BRows present in both A and B
A EXCEPT BRows in A but not in B
CARTESIAN PRODUCT
S11 Explain the Cartesian Product (CROSS JOIN) operation with an example. ▾
ANSWER
The Cartesian Product (also called CROSS JOIN or cross product) combines every row of the first table with every row of the second table. If table A has m rows and table B has n rows, the result has m × n rows.

Example:
Table: Student
┌────────┬───────┐
│ RollNo │ Name │
├────────┼───────┤
│ 1 │ Alice │
│ 2 │ Bob │
└────────┴───────┘

Table: Course
┌──────────┬──────────┐
│ CourseID │ CName │
├──────────┼──────────┤
│ C01 │ Maths │
│ C02 │ Physics │
└──────────┴──────────┘

Cartesian Product (CROSS JOIN):
SELECT * FROM Student CROSS JOIN Course;

Result (2 × 2 = 4 rows):
┌────────┬───────┬──────────┬──────────┐
│ RollNo │ Name │ CourseID │ CName │
├────────┼───────┼──────────┼──────────┤
│ 1 │ Alice │ C01 │ Maths │
│ 1 │ Alice │ C02 │ Physics │
│ 2 │ Bob │ C01 │ Maths │
│ 2 │ Bob │ C02 │ Physics │
└────────┴───────┴──────────┴──────────┘
Cartesian Product is rarely used alone — it is typically followed by a JOIN condition (WHERE) to produce meaningful results. Without a condition, it generates a huge number of rows.

NORMALIZATION & DESIGN
L1 Consider the relation R(StudentID, StudentName, CourseID, CourseName, InstructorID, InstructorName) with FDs:
FD1: StudentID, CourseID → StudentName, CourseName, InstructorID
FD2: CourseID → CourseName
FD3: InstructorID → InstructorName

(a) Identify all candidate keys. (2 marks)
(b) Is R in 1NF? 2NF? Justify. (3 marks)
(c) Decompose R fully into 3NF with primary keys. (5 marks) ▾
DETAILED ANSWER
(a) Candidate Keys
From FD1, {StudentID, CourseID} determines all other attributes. CourseID alone cannot determine StudentID, and StudentID alone cannot determine CourseID.
Candidate Key: {StudentID, CourseID} — the only candidate key.

(b) Normal Form Analysis
1NF: Yes — all attributes are atomic. ✓

2NF: No — partial dependency exists. FD2: CourseID → CourseName means CourseName depends on CourseID (part of the candidate key). This violates 2NF. ✗

(c) Decomposition to 3NF
Step 1: Remove partial dependencies → 2NF
R1(StudentID, CourseID, InstructorID)  — Enrollment
R2(CourseID, CourseName)  — Course

Step 2: Remove transitive dependencies → 3NF
In R1: {StudentID, CourseID} → InstructorID. But FD3 says InstructorID → InstructorName. We need a separate Instructor table.
Enrollment(StudentID, CourseID, InstructorID)
  PK: {StudentID, CourseID}, FK: InstructorID → Instructor
Course(CourseID, CourseName)
  PK: CourseID
Instructor(InstructorID, InstructorName)
  PK: InstructorID
All three relations are in 3NF (and BCNF) — no partial or transitive dependencies. Decomposition is lossless and dependency-preserving.

TRANSACTIONS & CONCURRENCY
L3 Given T1, T2, T3 on data items A and B:
T1: Read(A); A = A − 500; Write(A); Read(B); B = B + 500; Write(B)
T2: Read(A); A = A × 1.1; Write(A)
T3: Read(B); B = B − 200; Write(B)

(a) What anomaly arises if T1 and T2 run concurrently? (2 marks)
(b) Apply 2PL to T1 and T2. Show the lock table. (4 marks)
(c) How could deadlock occur between T1 and T3? Explain wait-die. (4 marks) ▾
DETAILED ANSWER
(a) Lost Update Problem
Assume A = 1000 initially.
T1 reads A=1000, computes A=500
T2 reads A=1000 (misses T1's update), computes A=1100
T1 writes A=500
T2 writes A=1100 — overwrites T1!
Final A=1100. T1's debit of 500 is lost.

(b) Two-Phase Locking (Strict 2PL)
TimeT1T2Locks
1Lock-X(A): GrantedA: X(T1)
2Read(A)=1000
3A=500, Write(A)
4Lock-X(A): WAITA: X(T1)
5Lock-X(B): GrantedB: X(T1)
6Read(B)=500, B=1000, Write(B)
7COMMIT (unlock A, B)
8Lock-X(A): GrantedA: X(T2)
9Read(A)=500, A=550, Write(A)
10COMMIT
Final: A=550, B=1000. Both updates preserved.

(c) Deadlock & Wait-Die
Scenario: T1 holds Lock-X(A), requests Lock-X(B). T3 holds Lock-X(B), requests Lock-X(A). Circular wait → deadlock.

Wait-Die Scheme (non-preemptive):
Assume T1=100 (older), T3=200 (younger).
  • T1 (older) requests lock held by T3 (younger): T1 waits.
  • T3 (younger) requests lock held by T1 (older): T3 dies (aborts, restarts with same timestamp).
Wait-Die prevents deadlock by ensuring at least one transaction in any cycle is aborted. It is a deadlock prevention scheme.
ADVANCED SQL
L4 Write SQL queries using:
Employee(EmpID, Name, Dept, Salary, ManagerID, JoinDate)
Department(DeptID, DeptName, Location)

(a) Employees earning more than their manager. (2 marks)
(b) Departments where no employee earns below ₹30,000. (2 marks)
(c) Each department name with employee count and average salary, sorted by avg salary desc. (3 marks)
(d) Employees who joined in the last 2 years in "IT" or "Finance". (3 marks) ▾
DETAILED ANSWER
(a) Employees earning more than their manager
SELECT e.Name
FROM Employee e
JOIN Employee m ON e.ManagerID = m.EmpID
WHERE e.Salary > m.Salary;

(b) Departments with no employee below ₹30,000
SELECT d.DeptName
FROM Department d
WHERE d.DeptID NOT IN (
  SELECT e.Dept FROM Employee e WHERE e.Salary < 30000
);
Or using HAVING:
SELECT d.DeptName
FROM Department d
JOIN Employee e ON d.DeptID = e.Dept
GROUP BY d.DeptID, d.DeptName
HAVING MIN(e.Salary) >= 30000;

(c) Department name, count, avg salary (sorted desc)
SELECT d.DeptName,
  COUNT(e.EmpID) AS EmployeeCount,
  AVG(e.Salary) AS AvgSalary
FROM Department d
LEFT JOIN Employee e ON d.DeptID = e.Dept
GROUP BY d.DeptID, d.DeptName
ORDER BY AvgSalary DESC;

(d) IT/Finance employees, joined in last 2 years
SELECT e.*
FROM Employee e
JOIN Department d ON e.Dept = d.DeptID
WHERE e.JoinDate >= DATE_SUB(CURDATE(), INTERVAL 2 YEAR)
  AND d.DeptName IN ('IT', 'Finance');
L5 Write short notes on any TWO of the following (5 marks each):
(a) Indexing in DBMS — types, dense vs sparse, B+ Tree indexing.
(b) Normalization — 1NF, 2NF, 3NF, BCNF with examples, when to stop.
(c) Transaction states — active, partially committed, committed, failed, aborted with state diagram.
(d) Concurrency problems — lost update, dirty read, unrepeatable read with examples. ▾
DETAILED ANSWER
(a) Indexing in DBMS

Types of Indexes:
TypeDescription
Primary IndexSparse index on the ordering key field
Clustering IndexSparse index on a non-key ordering field
Secondary IndexDense index on a non-ordering field

Dense vs Sparse: Dense has an entry for every key value (faster lookup, larger index). Sparse has entries for some keys (smaller, may need block scan).

B+ Tree: Balanced tree where data pointers are only in leaf nodes, internal nodes are routers, and leaves are linked for range scans. High fanout → shorter tree → fewer disk I/Os.

(b) Normalization
1NF: Atomic values, no repeating groups. Violation: Student with PhoneNumbers list. Fix: separate Phone table.

2NF: 1NF + no partial dependency. Violation: Enrollment(StudentID, CourseID, StudentName). Fix: separate Student table.

3NF: 2NF + no transitive dependency. Violation: Employee(EmpID, DeptID, DeptName). Fix: separate Department table.

BCNF: 3NF + for every FD X→Y, X is a super key. Stricter than 3NF.

When to stop: At BCNF (or 3NF if BCNF loses FDs). Further normalization (4NF/5NF) is rarely needed in practice.

(c) Transaction States
StateDescription
ActiveTransaction is executing
Partially CommittedAfter final statement executed (changes may be in buffers)
CommittedChanges written permanently to disk
FailedCannot proceed due to error
AbortedRolled back to initial state

State Diagram:
Active → Partially Committed → Committed
Active → Failed → Aborted

(d) Concurrency Problems
1. Lost Update: T1 reads A=100, writes A=70. T2 reads A=100, writes A=110. T1's update overwritten. Final A=110.
Solution: Locking or timestamp ordering.

2. Dirty Read: T1 writes A=70 (uncommitted). T2 reads A=70. T1 aborts. T2 read invalid data.
Solution: Strict 2PL (write locks held until commit).

3. Unrepeatable Read: T1 reads A=100. T2 writes A=200 and commits. T1 reads A again → 200. Same transaction sees different values.
Solution: Repeatable Read isolation level or snapshot isolation.
DBMS FUNDAMENTALS
L6 Write short notes on the following DBMS concepts:
(a) Data independence
(b) Data abstraction
(c) Data redundancy
(d) Characteristics of DBMS
(e) Example of DBMS
(f) Data integrity
(g) Data inconsistency
(h) Referential integrity ▾
DETAILED ANSWER
(a) Data Independence
Data independence is the ability to modify the schema at one level without affecting the schema at the next higher level. Two types:
  • Physical Independence: Changing physical storage (file organization, indexing) without affecting logical schema. Example: Adding an index to speed up queries — no change to application code.
  • Logical Independence: Changing logical schema (adding/removing columns, tables) without affecting external views. Example: Adding a new column 'Phone' to Student table — existing views/queries that don't use Phone still work.
This is achieved through the three-schema architecture (physical, logical, view).

(b) Data Abstraction
Data abstraction hides the complexity of data storage and provides a simplified interface. Three levels:
  • Physical Level: How data is actually stored on disk (blocks, pages, indexing). Lowest level.
  • Logical Level: What data is stored and relationships among them. Describes tables, rows, columns, constraints.
  • View Level: Part of the database visible to specific users. Hides irrelevant data for security and simplicity.


(c) Data Redundancy
Redundancy means storing the same data in multiple places. In file systems, redundancy is high (same data in different files). In DBMS, redundancy is controlled and minimized through:
  • Normalization — decomposing tables to eliminate duplication.
  • Centralized storage — single source of truth.
Problems caused by redundancy: wasted storage, data inconsistency, update anomalies, insertion/deletion anomalies.

(d) Characteristics of DBMS
  • Self-describing nature: DBMS stores metadata (data dictionary) about itself.
  • Data independence: Separation of data and programs.
  • Controlled redundancy: Minimizes duplication while allowing some for performance.
  • Data integrity: Constraints ensure accuracy and consistency.
  • Data security: User authentication, role-based access, encryption.
  • Concurrent access: Multiple users can access simultaneously with ACID guarantees.
  • Backup and recovery: Automated recovery from crashes and failures.
  • Data sharing: Multiple applications and users share the same data.
  • Query language: SQL for easy data retrieval and manipulation.

PostgreSQLRelational (ORDBMS)Open-source, object-relational, ACID

Microsoft SQL ServerRelational (RDBMS)Windows ecosystem, BI tools
SQLiteRelational (RDBMS)Embedded, serverless, lightweight


(f) Data Integrity
Data integrity ensures accuracy, consistency, and validity of data. Types:
  • Entity Integrity: Primary key must be unique and NOT NULL.
  • Referential Integrity: Foreign key values must match a primary key or be NULL.
  • Domain Integrity: Column values must fall within a defined domain (data type, CHECK constraint).
  • User-defined Integrity: Business rules specific to an application.


(g) Data Inconsistency
Data inconsistency occurs when different copies of the same data have different values. Caused by:
  • Uncontrolled redundancy — same data updated in one place but not others.
  • Concurrent access without proper locking — dirty reads, lost updates.
  • Lack of integrity constraints — invalid data entered.
Solution: Normalization, ACID transactions, integrity constraints.

(h) Referential Integrity
Referential integrity ensures that a foreign key value in one table must either match a primary key value in the referenced table or be NULL. It prevents orphan records.
CREATE TABLE Enrollment (
  StudentID INT,
  CourseID INT,
  PRIMARY KEY (StudentID, CourseID),
  FOREIGN KEY (StudentID) REFERENCES Student(StudentID)
    ON DELETE CASCADE ON UPDATE CASCADE,
  FOREIGN KEY (CourseID) REFERENCES Course(CourseID)
    ON DELETE CASCADE ON UPDATE CASCADE
);
Referential actions: CASCADE, SET NULL, SET DEFAULT, NO ACTION, RESTRICT.
ARCHITECTURE
L7 Explain the following DBMS architectures with diagrams:
(a) Three-Schema Architecture (ANSI/SPARC Architecture)
(b) Three-Tier Architecture ▾
DETAILED ANSWER
(a) Three-Schema Architecture (ANSI/SPARC)
Proposed by ANSI/SPARC in 1975, this architecture separates the database into three levels to achieve data independence.

1. Internal (Physical) Level
Describes how data is physically stored on storage media. Deals with:
  • Storage structures (files, pages, blocks)
  • Indexing methods (B+ Tree, hash)
  • Data compression and encryption
  • Record placement and access paths

2. Conceptual (Logical) Level
Describes what data is stored and the relationships among them. Hides physical details.
  • Entities, attributes, relationships
  • Constraints and business rules
  • Tables, views, schemas

3. External (View) Level
Describes how different users see the data. Each user has their own view.
  • Hide irrelevant data for security
  • Provide customized representation
  • Multiple views over same conceptual schema

Mapping between levels:
External/Conceptual Mapping → Logical Data Independence
Conceptual/Internal Mapping → Physical Data Independence


(b) Three-Tier Architecture
Separates an application into three logical layers for modularity, scalability, and security.

1. Presentation Tier (Client Tier)
  • User interface — web browser, mobile app, desktop client
  • Handles user interaction and display
  • Does NOT directly access the database

2. Application Tier (Business Logic / Middle Tier)
  • Contains business logic, rules, validations
  • Processes client requests and coordinates
  • Acts as a bridge between presentation and database
  • Examples: Java EE, .NET, Node.js, Django, Flask

3. Database Tier (Data Tier)
  • Manages data storage and retrieval
  • DBMS runs here (MySQL, Oracle, PostgreSQL)
  • Handles data integrity, security, transactions

Architecture Diagram:
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│ Presentation│────→│ Application │────→│ Database │
│ Tier │ │ Tier │ │ Tier │
│ (Client) │←────│ (Middleware)│←────│ (DBMS) │
└─────────────┘ └─────────────┘ └─────────────┘
Advantages: Scalability (each tier can scale independently), security (client never directly accesses DB), maintainability (changes in one tier don't affect others), reusability (same business logic for web + mobile).
SQL CLAUSES & FUNCTIONS
L8 Explain the following SQL clauses and functions with examples:
WHERE, LIKE, ORDER BY, GROUP BY, BETWEEN, Functions (String, Date, Numeric), SUM, COUNT, MIN, MAX, AVG ▾
DETAILED ANSWER
Assume the following table for all examples:
Employee(EmpID, Name, Dept, Salary, City, JoinDate)

1. WHERE — Filters rows before grouping/aggregation.
SELECT * FROM Employee WHERE Salary > 50000;
SELECT * FROM Employee WHERE Dept = 'IT' AND City = 'Bangalore';

2. LIKE — Pattern matching with wildcards: % (any sequence) and _ (single character).
SELECT * FROM Employee WHERE Name LIKE 'A%';   -- Names starting with 'A'
SELECT * FROM Employee WHERE Name LIKE '%esh';   -- Names ending with 'esh'
SELECT * FROM Employee WHERE Name LIKE '_a%';   -- Second letter is 'a'
SELECT * FROM Employee WHERE City LIKE '%pur%';   -- City contains 'pur'

3. ORDER BY — Sorts result set (ASC default, DESC for descending).
SELECT * FROM Employee ORDER BY Salary DESC;
SELECT * FROM Employee ORDER BY Dept ASC, Salary DESC;

4. GROUP BY — Groups rows that have the same values, used with aggregate functions.
SELECT Dept, COUNT(*) AS EmpCount FROM Employee GROUP BY Dept;
SELECT Dept, AVG(Salary) AS AvgSal FROM Employee GROUP BY Dept;

5. BETWEEN — Filters values in a range (inclusive).
SELECT * FROM Employee WHERE Salary BETWEEN 30000 AND 70000;
SELECT * FROM Employee WHERE JoinDate BETWEEN '2023-01-01' AND '2024-12-31';

6. SQL Functions

String Functions:
SELECT UPPER(Name) FROM Employee;   -- Convert to uppercase
SELECT LOWER(Name) FROM Employee;   -- Convert to lowercase
SELECT LENGTH(Name) FROM Employee;   -- Length of string
SELECT CONCAT(Name, ' - ', Dept) FROM Employee;   -- Concatenate strings
SELECT SUBSTR(Name, 1, 3) FROM Employee;   -- First 3 characters
SELECT TRIM(' Hello ');   -- Remove leading/trailing spaces

Date Functions:
SELECT CURDATE();   -- Current date
SELECT YEAR(JoinDate) FROM Employee;   -- Extract year
SELECT MONTH(JoinDate) FROM Employee;   -- Extract month
SELECT DATEDIFF(CURDATE(), JoinDate) FROM Employee;   -- Days between dates
SELECT DATE_ADD(JoinDate, INTERVAL 1 YEAR) FROM Employee;

Numeric Functions:
SELECT ROUND(Salary, -3) FROM Employee;   -- Round to nearest 1000
SELECT ABS(-50);   -- Absolute value
SELECT CEIL(4.2), FLOOR(4.8);   -- 5, 4
SELECT MOD(10, 3);   -- 1 (remainder)

7. Aggregate Functions — Used with GROUP BY or on entire table.
SELECT SUM(Salary) FROM Employee;   -- Total salary
SELECT COUNT(*) FROM Employee;   -- Total rows
SELECT COUNT(DISTINCT Dept) FROM Employee;   -- Unique departments
SELECT MIN(Salary), MAX(Salary) FROM Employee;   -- Min and max salary
SELECT AVG(Salary) FROM Employee;   -- Average salary

Combined Example:
SELECT Dept,
  COUNT(*) AS EmployeeCount,
  AVG(Salary) AS AvgSalary,
  MIN(Salary) AS MinSalary,
  MAX(Salary) AS MaxSalary
FROM Employee
WHERE City LIKE '%pur%'
GROUP BY Dept
HAVING AVG(Salary) > 40000
ORDER BY AvgSalary DESC;
Order of execution: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
JOIN OPERATIONS
L9 Explain different types of JOIN operations in SQL with examples.
INNER JOIN, LEFT JOIN, RIGHT JOIN, FULL JOIN, CROSS JOIN, SELF JOIN, NATURAL JOIN ▾
DETAILED ANSWER
JOINs combine rows from two or more tables based on a related column.

Sample tables:
Students: Courses:
┌─────┬───────┬────────┐ ┌─────┬──────────┐
│ Sid │ SName │ Cid │ │ Cid │ CName │
├─────┼───────┼────────┤ ├─────┼──────────┤
│ 1 │ Alice │ C01 │ │ C01 │ Maths │
│ 2 │ Bob │ C02 │ │ C02 │ Physics │
│ 3 │ Carol │ C03 │ │ C04 │ Chemistry│
└─────┴───────┴────────┘ └─────┴──────────┘

1. INNER JOIN — Returns rows where there is a match in both tables.
SELECT S.SName, C.CName
FROM Students S
INNER JOIN Courses C ON S.Cid = C.Cid;
Result: Alice-Maths, Bob-Physics. Carol excluded (C03 has no match in Courses).

2. LEFT JOIN (LEFT OUTER JOIN) — All rows from left table, matching rows from right. NULLs where no match.
SELECT S.SName, C.CName
FROM Students S
LEFT JOIN Courses C ON S.Cid = C.Cid;
Result: Alice-Maths, Bob-Physics, Carol-NULL.

3. RIGHT JOIN (RIGHT OUTER JOIN) — All rows from right table, matching rows from left. NULLs where no match.
SELECT S.SName, C.CName
FROM Students S
RIGHT JOIN Courses C ON S.Cid = C.Cid;
Result: Alice-Maths, Bob-Physics, NULL-Chemistry.

4. FULL JOIN (FULL OUTER JOIN) — All rows from both tables. NULLs where no match.
SELECT S.SName, C.CName
FROM Students S
FULL JOIN Courses C ON S.Cid = C.Cid;
Result: Alice-Maths, Bob-Physics, Carol-NULL, NULL-Chemistry.

5. CROSS JOIN (Cartesian Product) — Every row of table A paired with every row of table B.
SELECT S.SName, C.CName
FROM Students S
CROSS JOIN Courses C;
Result: 3 Students × 3 Courses = 9 rows.

6. SELF JOIN — Joining a table with itself. Requires table aliases.
SELECT e1.Name AS Employee, e2.Name AS Manager
FROM Employee e1
JOIN Employee e2 ON e1.ManagerID = e2.EmpID;


7. NATURAL JOIN — JOIN based on columns with the same name. MySQL uses matching column names automatically.
SELECT * FROM Students NATURAL JOIN Courses;
NATURAL JOIN is risky — it matches ALL columns with same names. Best practice: use INNER JOIN with explicit ON condition.
ER MODEL (HIGH PRIORITY)
L10 Explain the Entity-Relationship (ER) Model in detail, covering:
(a) Entities, attributes, and relationships
(b) Types of attributes and keys
(c) Cardinality and participation constraints
(d) Weak entities and generalization/specialization
(e) How to convert an ER diagram into relational schema ▾
DETAILED ANSWER
(a) Entities, Attributes, and Relationships
Entity: A real-world object distinguishable from others (e.g., a Student, a Car). Represented by a rectangle in ER diagrams.
Attribute: Properties that describe an entity (e.g., Student: RollNo, Name, Age). Represented by an ellipse.
Relationship: Association between entities (e.g., Student enrolls in Course). Represented by a diamond.

(b) Types of Attributes
Attribute TypeDescriptionER Notation
SimpleAtomic, cannot be divided (e.g., Age)Single ellipse
CompositeCan be subdivided (e.g., Name = First + Last)Ellipse with sub-ellipses
MultivaluedMultiple values (e.g., PhoneNumbers)Double ellipse
DerivedCalculated from others (e.g., Age from DOB)Dashed ellipse
KeyUniquely identifies entity (e.g., RollNo)Underlined attribute

Types of Keys:
  • Super Key: Set of attributes that uniquely identifies a tuple.
  • Candidate Key: Minimal super key (no proper subset is a super key).
  • Primary Key: Selected candidate key (NOT NULL, unique). Underlined in ER diagram.
  • Foreign Key: References primary key of another table.


(c) Cardinality and Participation Constraints
Cardinality — Maximum number of relationship instances an entity can participate in:
1:1 — One-to-One (Person ↔ Aadhaar Card)
1:N — One-to-Many (Department → Employees)
M:N — Many-to-Many (Students ↔ Courses)

Participation — Minimum number of relationship instances:
  • Total (mandatory): Every entity must participate (double line). Example: Every Employee must belong to a Department.
  • Partial (optional): Some entities may not participate (single line). Example: A Student may or may not live in a Hostel.


(d) Weak Entities and Generalization/Specialization
Weak Entity: An entity that cannot be uniquely identified by its own attributes alone; depends on an identifying relationship with a strong entity.
  • Represented by a double rectangle.
  • Identifying relationship: double diamond.
  • Example: Payment (PaymentID is only unique within a specific Order).
  • Weak entity has a partial key (dashed underline).

Generalization: Combining common attributes of lower-level entities into a higher-level entity (bottom-up).
Specialization: Creating sub-groups from a higher-level entity (top-down).
Example: Person generalized into Student and Employee; Student specialized into UG and PG.

(e) ER-to-Relational Mapping
Steps to convert ER diagram to relational schema:
  1. Strong entity → A table with primary key.
  2. Weak entity → Table with foreign key referencing strong entity's PK; PK = partial_key + FK.
  3. 1:1 Relationship → Add FK in either entity (prefer the one with total participation).
  4. 1:N Relationship → Add FK in the N-side entity referencing PK of 1-side.
  5. M:N Relationship → New table with FKs referencing both entity PKs; PK = (FK1, FK2).
  6. Multivalued attribute → New table with FK referencing entity's PK.
  7. Composite attribute → Only component attributes are included.
  8. Derived attribute → Not stored; computed when needed.

Example — ER to Relational:
Student(SID, Name) — strong entity
Course(CID, Title) — strong entity
Enrolls(SID, CID, Grade) — M:N relationship table
NORMALIZATION & CLOSURE / BCNF
L11 Explain Normalization, Attribute Closure, and BCNF decomposition:
(a) 1NF, 2NF, 3NF, BCNF with examples
(b) Attribute closure — how to find candidate keys
(c) BCNF property and decomposition algorithm
(d) Demonstrate with a complete example ▾
DETAILED ANSWER
(a) Normal Forms
1NF (First Normal Form):
  • Every attribute contains only atomic (indivisible) values.
  • No repeating groups or arrays.
Violation: Student with PhoneNumbers = {98765, 54321}
Fix: Separate Phone table or store one phone per row.

2NF (Second Normal Form):
  • In 1NF + no partial dependency.
  • Partial dependency: non-key attribute depends on part of a composite candidate key.
Violation: Enrollment(StudentID, CourseID, StudentName) — StudentName depends on StudentID (part of PK).
Fix: Split into Enrollment(StudentID, CourseID) and Student(StudentID, StudentName).

3NF (Third Normal Form):
  • In 2NF + no transitive dependency.
  • Transitive dependency: non-key attribute depends on another non-key attribute.
Violation: Employee(EmpID, DeptID, DeptName) — DeptName depends on DeptID (not on EmpID directly).
Fix: Employee(EmpID, DeptID) and Department(DeptID, DeptName).

BCNF (Boyce-Codd Normal Form):
  • In 3NF + for every non-trivial FD X → Y, X must be a super key.
  • Stricter than 3NF — every BCNF is in 3NF, but not vice versa.


(b) Attribute Closure — Finding Candidate Keys
Definition: Closure of attribute set X (denoted X+) is the set of all attributes that can be functionally determined by X.

Algorithm:
closure = X
repeat:
  for each FD A → B:
    if A ⊆ closure: closure = closure ∪ B
until no change

Example: R(A, B, C, D, E) with FDs: AB → C, C → D, D → E, B → A

Find all candidate keys:
B+ = {B, A, C, D, E} = all attributes → B is a candidate key.
AB+ = {A, B, C, D, E} → AB is a super key but NOT minimal (B alone is sufficient).
So, Candidate Key = {B}


(c) BCNF Decomposition Algorithm
Given relation R and set of FDs F:
1. Find a FD X → Y that violates BCNF (X is NOT a super key).
2. Decompose R into:
  R1 = X ∪ Y
  R2 = R − Y
3. Repeat for R1 and R2 until all relations are in BCNF.

(d) Complete Example
R(StudentID, CourseID, InstructorID, InstructorDept, Grade)
FDs: StudentID, CourseID → Grade, InstructorID
      InstructorID → InstructorDept
      CourseID → InstructorID

Step 1 — Find candidate keys:
{StudentID, CourseID}+ = {StudentID, CourseID, Grade, InstructorID, InstructorDept}
→ Candidate Key: {StudentID, CourseID}

Step 2 — Check BCNF violations:
FD1: StudentID, CourseID → Grade, InstructorID — X is CK, OK.
FD2: InstructorID → InstructorDept — X is NOT a super key. VIOLATION
FD3: CourseID → InstructorID — X is NOT a super key. VIOLATION

Step 3 — Decompose:
Take FD3 violation first: CourseID → InstructorID
R1({StudentID, CourseID, Grade, InstructorID}) — keep CourseID as FK
R2({CourseID, InstructorID})

In R2: CourseID → InstructorID, InstructorID → InstructorDept (still violates)
Decompose R2 further:
R2a({CourseID, InstructorID}) — now in BCNF
R2b({InstructorID, InstructorDept}) — in BCNF

Final BCNF decomposition:
Enrollment(StudentID, CourseID, Grade)
Teaches(CourseID, InstructorID)
Instructor(InstructorID, InstructorDept)
BCNF decomposition is lossless and preserves data. However, it may NOT preserve all FDs — in that case, 3NF is preferred.
